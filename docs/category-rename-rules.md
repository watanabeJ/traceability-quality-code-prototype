# 品类改名规则

## 适用范围

确认日期：2026-10-30。适用于品类管理、订单创建与详情、绑定申请、产品编辑、统计和扫码资料。

本次只调整内部规则和需求说明，不新增业务表单、按钮或页面。

## 业务规则

1. 产品大类允许纠错和规范化更名。改变品类含义时必须新建品类。例如，“茶业”可纠正为“茶叶”；“茶叶”改成“香烟”或缩小为“碧螺春”须新建品类。
2. 改名后，订单、统计和品类选择显示最新名称。未绑定产品的草稿和待审核资料使用最新名称。已绑定产品及扫码资料不自动修改，曾绑定后重置的产品也保留原资料。
3. 改名不改变品类 ID、产品号、订单归属、码量和审批状态。同品类校验按 ID 判断，不能因为名称不同而拒绝追加绑定、保存、重提或审核。
4. 每次改名记录修改前后名称、操作人和时间。订单已有品类快照不覆盖；快照用于还原创建时信息，修改记录用于追踪变更。

“纠错”和“改变业务含义”由运营人员按上述规则判断。本版不增加语义识别或改名审批功能，不能声称系统会自动拦截所有改变含义的更名。

## 内部处理

- 订单明细的 `category` 为当前展示名称，`categorySnapshot` 保存创建时名称。改名刷新展示名称时，不覆盖已有快照。
- 产品的 `category` 和 `details.category` 属于产品资料。已绑定产品保留原值，不对其执行全量名称替换。
- 旧产品草稿在再次保存或提交时，从原订单明细的品类 ID 取得最新名称。已绑定产品的资料编辑保留原品类文字，不因主数据改名被动更新。
- 绑定校验优先使用品类 ID。旧数据缺少 ID 时，按产品号解析；再缺少产品号时，仅用当前唯一名称解析。明确存在但失效的 ID 不得按同名或产品号降级放行。
- 缺少身份且无法唯一解析的历史数据不能自动认定为同品类。应先核对原始订单，补齐身份；不覆盖原产品公开资料。
- 统计以固定产品号聚合，同一品类改名前后的订单不拆组；显示和品类关键词筛选采用当前名称。
- 两个同源页面间收到品类存储变更后更新内部名称。未关闭的业务弹窗不强制重建，避免丢失输入；后续保存和审核重新校验身份。

## 对应实现

- `js/core/category-management.js`：身份解析、名称同步、改名审计及跨页更新。
- `js/core/order-management.js`：同品类绑定、编辑及重提校验。
- `js/core/order-statistics.js`：统计标签和产品大类搜索。
- `prototype-annotator/annotations.json`：相关页面的局部批注。
