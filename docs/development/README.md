# 溯源质控码平台开发文档

## 1. 文档用途

本目录根据当前 `prototype-multipage` 多页面系统的实际页面、业务数据和交互逻辑整理，用于产品确认、前后端开发、数据库设计、接口设计和测试验收。

- 核对日期：2026-08-20
- 代码基线：`prototype-multipage/main`，提交 `b05bb83`

当前原型使用浏览器存储模拟数据持久化，因此本文档分为两类内容：

- **现行规则**：已经在当前系统中实现或经过确认，正式开发应保持一致。
- **落地建议**：原型无法完整表达，但正式后端必须补充的事务、并发、审计和异步任务要求。

## 3. 系统角色与边界

| 端 | 当前角色 | 核心职责 |
| --- | --- | --- |
| 运营端 | 启用状态的运营账号 | 客户与账号管理、生成码段、分配码段、绑定审核、直接绑定、撤回审核 |
| 客户端 | 启用状态的客户账号 | 查看本人订单、维护产品资料、发起绑定申请、发起产品撤回、查看通知 |
| 扫码端 | 匿名消费者 | 根据单个序列号查看已激活产品资料或码状态 |

当前原型中所有运营账号权限一致，尚未实现“管理员、审核员、订单专员”等岗位级授权。正式系统如需细分角色，应在现有运营端权限之上增加 RBAC，不应改变客户数据隔离规则。

## 4. 核心业务对象

系统必须区分以下对象：

1. **库存码段批次**：平台生成的一段连续序列号，是库存来源。
2. **分配订单**：运营端从库存批次切出连续码段并分配给一个客户后形成的业务记录。
3. **产品**：客户维护的五模块溯源资料及产品批次信息。
4. **绑定申请**：客户申请把某个订单中的连续可用码段绑定到产品。
5. **激活记录**：绑定审核通过或运营端直接绑定后形成的实际产品与码段关系。
6. **撤回申请**：客户申请重置一个或多个已经激活的具体码段。

这些对象不可合并为一个“二维码状态”字段。库存归属、客户分配、产品绑定和扫码展示分别由不同记录决定。

## 5. 关键数量口径

同一分配订单中：

```text
订单码量 = 已激活码量 + 绑定申请中码量 + 剩余可用码量
剩余可用码量 = 订单码量 - 已激活码量 - 绑定申请中码量
```

其中：

- 已激活码量只统计状态不是“已重置”的有效激活区间，并按区间合并后去重。
- 绑定申请中码量只统计“待审批”的绑定申请和“待审核”的新建产品并绑定申请。
- 已驳回、已撤回和草稿申请不占用码量。
- 已撤销分配的订单不再计入客户码量，其码段恢复为来源库存批次的可用范围。

## 6. 当前实现依据

主要事实来源：

- `js/core/domain.js`：实体归一化、码段计算、数据关系和下载包生成。
- `js/core/enhanced-runtime.js`：登录、生成、分配、审核、撤销、撤回等业务动作。
- `js/components/application.js`：数量口径、筛选规则和当前绑定状态计算。
- `js/views/business.js`：运营端和客户端实际页面信息。
- `js/views/scan.js`：扫码状态解析和公开信息范围。

## 7. 已知原型限制

- 当前数据保存在 `localStorage`，不具备服务端并发控制和真正的权限隔离。
- 二维码大批量完整下载在原型中只生成任务占位包；正式系统必须由后端异步生成真实压缩包。
- 当前站内信是本地数据，正式系统需要可靠消息写入和已读状态持久化。
- 当前绑定申请编号生成器包含固定月份示例，正式系统必须统一使用服务端时间和统一编号服务。
- 当前扫码次数保存在浏览器本地，正式系统必须由服务端按码记录并防刷。
- 原型中的文件以 Data URL 或本地资源模拟，正式系统应使用对象存储和文件元数据表。

## 8. 文档维护规则

- 业务规则发生变化时，优先修改规则说明和状态流转，再修改实现。
- 新增状态必须同时更新数据字典、权限矩阵和状态流转图。
- 新增关键操作必须定义前置条件、事务影响、失败行为和审计字段。
- 页面展示字段变化不等于新增业务实体；数据库设计以实际业务关系为准。
