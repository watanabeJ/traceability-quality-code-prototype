# 权限矩阵

## 1. 当前权限模型

当前系统存在三类访问主体：

- **运营账号**：所有启用运营账号权限一致。
- **客户账号**：只访问本客户数据。
- **匿名扫码用户**：只通过序列号读取允许公开的溯源信息。

状态为“禁用”的运营账号或客户账号不能登录，也不能继续执行已打开页面中的业务操作。

## 5. 数据隔离规则

1. 客户端所有查询必须由服务端从登录身份取得 `customer_id`，不能信任请求参数中的客户编号。
2. 客户端访问订单、产品、绑定申请、撤回申请、消息和附件时必须同时校验 `customer_id`。
3. 绑定申请中的订单和产品必须属于同一客户。
4. 激活记录中的订单、产品和客户必须一致。
5. 撤回申请只能引用申请客户自己的产品和激活记录。
6. 扫码端只按序列号返回公开视图模型，不直接返回产品资料表或内部业务对象。
7. 文件下载必须使用鉴权签名地址；公开扫码附件和后台私有附件使用不同访问策略。

## 6. 正式 RBAC 扩展建议

当前原型没有岗位差异。若正式系统需要细分，可在不改变上述数据范围的前提下拆分：

| 建议角色 | 建议权限 |
| --- | --- |
| 平台管理员 | 运营账号、客户账号、全部业务和配置 |
| 码段运营 | 生成、下载、库存分配、撤销分配、订单查看 |
| 审核专员 | 产品资料查看与编辑、绑定审核、撤回审核 |
| 只读审计 | 全局查询、导出和审计日志，不允许业务修改 |

正式开发前应由业务方确认是否启用上述拆分；未确认时以“所有启用运营账号权限一致”为现行规则。
